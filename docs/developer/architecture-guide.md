# Architecture Guide

## Responsibility boundary: Rust does the work, Svelte draws it

Ostralith is split along one rule: **anything heavy, privileged or
security-relevant happens in Rust; the webview does presentation and
interaction only.**

| Rust (`src-tauri/`) owns | Svelte (`src/`) owns |
| --- | --- |
| All file reads and writes (vault, attachments, imports/exports, settings) | Layout, tabs, views, the editor UI |
| Markdown/link parsing for indexing, file watching | The command palette and fuzzy ranking of lists it already has |
| SQLite, indexing, embeddings, search | In-window keydown dispatch through the command registry |
| Model runtimes, sidecars, audio, git and sync | Forms, the settings UI, rendering streamed tokens and transcripts |
| Encryption and the keychain | Canvas and PDF rendering |
| **All network access** (`ostralith-net`) | |
| Global (OS-wide) shortcuts, system integration, permission enforcement | |

Rules that keep the boundary honest:

- The frontend never touches disk, network or OS APIs directly. It calls typed
  commands from `$lib/tauri-bindings`. ast-grep `no-raw-invoke` and `no-fetch`
  plus the CSP enforce this (see [Quality](quality.md) and
  [Privacy & Network](privacy.md)).
- `@tauri-apps/plugin-fs` is not used by the UI; the Rust plugin is only there
  for scope persistence.
- Long-running work streams back over `tauri::ipc::Channel<T>`; broadcasts use
  events.
- Rust errors that the UI must react to are `ostralith_core::CoreError`
  (tagged by `kind`); `src/lib/core-error.ts` renders them.

### Cargo workspace

New domains (vault, store, index, ai, audio, sync, plugin-host, …) arrive as
crates under `src-tauri/crates/`, each with its own tests. The app crate stays
thin: one `commands/<domain>.rs` per domain that adapts a crate to Tauri
(managed state, `#[tauri::command]`, events), registered in `bindings.rs`.
Shared dependency versions live in `[workspace.dependencies]`. Platform-only
dependencies go under `[target.'cfg(..)'.dependencies]`, never behind cargo
features, because CI runs clippy with `--all-features` on every OS.

### Sidecars

`bundle.externalBin` binaries (the upcoming `ml-worker`, model servers) are
built by `scripts/build-sidecars.mjs`. So that debug and CI builds never
fail on a missing binary, `build.rs` writes a zero-byte
`binaries/<name>-<target-triple>[.exe]` placeholder (with a cargo warning)
for each name in its `SIDECARS` list. The two lists must stay in sync, and
each new sidecar must also be added to `bundle.externalBin`. `binaries/` is
gitignored. Both lists are empty in Phase 0, so `build:sidecars` is not yet
part of `beforeBuildCommand`; add it there with the first sidecar.

The `$lib` alias in `vite.config.ts` maps to `src/lib`, so imports read
`$lib/stores/theme.svelte` rather than relative paths.

## Two Vite entry points

The main window and the Quick Pane are separate HTML documents, each mounting
its own Svelte app. `vite.config.ts` declares both in `build.rollupOptions.input`:

```ts
input: {
  main: path.resolve(__dirname, 'index.html'),
  'quick-pane': path.resolve(__dirname, 'quick-pane.html'),
},
```

In dev, Vite serves both from the project root. In production, Rollup outputs
two bundles. See [Quick Panes](quick-panes.md) for the full multi-window story.

## Boot sequence

### Rust (`lib.rs`)

1. Plugins register in order: single-instance first (so a second launch
   forwards its args, including deep links), then window-state,
   global-shortcut, deep-link, autostart, updater, log, fs, persisted-scope,
   os, opener, dialog.
2. `setup()` records the crash directory and startup time, then builds the
   managed state commands depend on: `init_network` (fatal on failure,
   because requests could not be policed otherwise) and `init_entitlements`.
3. Saved global shortcuts are registered, the Quick Pane window and tray are
   created (both non-fatal), and deep links are relayed to the frontend as
   `app:deep-link-received`.

### Frontend

`src/main.ts` runs synchronously before the first paint:

1. `paintFromHint()` — reads `localStorage['ui-theme']`, applies `.dark` class
2. `mount(App, ...)` — Svelte mounts `App.svelte`

`App.svelte`'s `onMount` first starts the listeners that need no saved state:

1. `initSquareCorners()`, `initTheme()`, `initQuickPaneBridge()`
2. `initNetwork()` + `initEntitlements()` — mirror the Rust policy and flags,
   set the `offline` / `pro` context keys, and follow their change events
3. `initBrowserKeySuppression()` — block webview accelerators (reload, find, …)
4. Listeners for `app:close-requested`, `tray:quit-requested` and
   `app:deep-link-received` (each URL goes to `routeDeepLink()`)

Then the async chain:

1. `initPreferences()` + `initAppState()` — load from disk in parallel
2. `reconcileTheme()` — authoritative preferences override the localStorage hint
3. `applyWindowEffects(prefs.windowEffects)` — native vibrancy IPC, before the
   window is shown so there is no opaque→translucent pop
4. `initializeLanguage(prefs.language)` — set i18next language
5. `initCommands()` — register all commands, wire the keydown handler, build
   menus, and run the one-time keymap migration (its toast needs the
   language from step 4)
6. `initTabs(appState)` — restore the tab strip. After the commands, so a
   restore problem can never leave the app without its shortcuts
7. Open the onboarding dialog if it has not been completed
8. `cleanupOldRecoveryFiles()` and `checkForRecentCrash()` in the background

The main window is created with `visible: false` in `tauri.conf.json`.
`App.svelte` calls `appWindow.show()` + `appWindow.setFocus()` at the end of
the chain (even if a step failed), so the user never sees an unstyled flash.

## Single dispatch path

Keyboard shortcuts, the command palette, and native menus all dispatch through
`executeCommand(id)` in `src/lib/commands/registry.svelte.ts`. No command body
is duplicated across input sources. Which command a key runs depends on its
`when` clause and the current context keys; see
[Commands & Shortcuts](commands-and-shortcuts.md).

## Workspace

The centre of the window is a tabbed workspace, not a router: tabs are
identified by `ostralith://` URIs and rendered by views looked up by kind.
See [Workspace](workspace.md).

## Svelte 5 patterns

**Function-based stores** — stores expose plain functions (`getPreferences()`,
`setPreference()`, `initPreferences()`) backed by module-level `$state` and
`$effect`. No class-based stores.

**`$state.snapshot()` before IPC** — Svelte 5 rune proxies do not serialise
over the Tauri IPC bridge. Every `invoke()` / `commands.*` call that sends
reactive state must wrap it with `$state.snapshot()` first. An ast-grep rule
(`snapshot-before-ipc.yml`) enforces this.

**tauri-specta bindings** — Rust commands are never called via raw `invoke()`.
All IPC goes through the generated `$lib/bindings.ts` and the typed re-export
in `$lib/tauri-bindings.ts`, which provides `unwrapResult()` for the
`Result<T, E>` envelope. Commands that the UI must branch on return
`CoreError` rather than `String`.

## Monorepo promotion

`lib/components/ui`, `stores`, and `utils` are cleanly separated already.
Promoting to a pnpm workspace later is mechanical: move each to its own
`packages/` directory, add a `package.json` with the appropriate exports, and
update import paths.
